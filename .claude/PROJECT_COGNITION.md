## 一、项目定义

这个项目的本质是：**高仿在线直播板书解题录屏 / 板书教学产品**

**不是什么：**
- 普通白板编辑器
- 通用画布工具
- 富文本编辑系统

**是什么：**
- 自动化工作流 / 多 agent 协作产品
- 教学自动剪辑 / 讲课板书录制工作台
- 围绕"板书解答问题、板书教学、录屏交付"的工作流系统

**工作流链路：**
```
用户上传题目 → 自动生成讲解与板书 → 控制播放/板书/标注 → 录屏交付
   第一步          第二步              第三步              第四步
```

## 二、核心真相源

### 前三步真相（保留，不动）

1. **第一步：上传识别**
   - 用户上传题目
   - 系统识别题目内容

2. **第二步：自动生成**
   - 自动生成讲解
   - 自动生成板书参数
   - 画布参数已经出现（包括标签等）

3. **第三步：当前流程**
   - 已验证正确
   - 参数、字段、样式都已产出

### 第四步真相（重构，只消费）

**第四步的唯一职责：消费、映射、渲染、录制上游真相**

- ✅ 消费前三步的参数
- ✅ 映射到舞台几何
- ✅ 渲染到 DOM / Canvas / Konva
- ✅ 录制成视频

**第四步禁止做的事：**
- ❌ 重新发明参数
- ❌ 创造第二套真相
- ❌ 改变 A/B/C 语义
- ❌ 引入新概念（如 zone）

## 三、硬规则：工作流继承与唯一真相

**所有参数定义、字段，以及会影响舞台结果的前端样式，都必须从上一个环节继承下来。**

### 四句检查法

改代码前必须问清楚：

1. **这个值从哪一环继承？** — 能否追溯到上游来源？
2. **当前层有没有重新定义第二套？** — 是否出现了重复定义？
3. **DOM / Canvas / Konva / 录制是否都在消费同一个来源？** — 是否对齐？
4. **如果这个值不是继承来的，这一步还算不算 workflow？** — 是否破坏了工作流？

**凡是答不清楚来源的值，不允许进入主线。**

## 五、ABC 三轨真相

### 定义（来自 globalRules.ts）

| 轨道 | 名称 | 职责 | 控制位置 | 唯一性 |
|------|------|------|---------|--------|
| A | 语音轨 | 语音/文本主轴，锚点内容 | 音轨上 | 语音主轴 |
| B | 寿命轨 | 寿命/显示窗口，"生死簿" | 音轨上 | 时间控制 |
| C | 角色轨 | 画布演员/板书内容/演绎资产 | 画布上 | 视觉演绎 |

### 生克关系

- B 寿命超过 A source 的尾巴 → C 静态留场，不拖慢书写
- B 寿命短于 A source → 只缩短显示窗口，不隐式改写 C 书写速度
- C 书写速度由 drawSpeed 控制，不由 B 寿命隐式改写

## 六、工作法则

### 1. 不要相信自己的印象

**硬规则：把真相落地写下足迹**

- 新进度 → 立刻记录
- 新认知 → 立刻记录
- 新禁止项 → 立刻记录
- 新怀疑点 → 立刻记录

没有记录就等于没有做。

### 2. 节点完成即时摘要

**协作模式：**
- 完成一个节点 → 立刻写简要足迹和摘要
- 做完一次 tree / 结构检查 → 立刻记录
- 不要等到上下文快满了才压缩

**为什么：**
- 避免有效上下文浪费在无意义的来回上
- 更容易保持施工锚点
- 靠印象记住"刚才为什么这样判断"非常不可靠

### 3. 控件责任表工程纪律

**功能组件封装前必须写责任表：**
- 这个控件干什么
- 负责什么
- 不负责什么
- 影响关系
- 来源依据 / 受什么影响
- 参数字段
- 对应前端
- 控件名称
- 是否唯一

**验收标准必须收紧：**
- 该有的功能要有
- 逻辑条理、映射关系、路由定义、契约边界都必须做到军工级别严谨
- 不能为了赶时间接受模糊行为、松散映射或边界漂移

### 4. Compact 前必须记足迹

**规则：**
- Compact 或大段打断前，必须先记录足迹
- 没有记录就等于没有做
